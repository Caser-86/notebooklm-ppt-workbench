# PPTX Import Pipeline Design

## Summary

This spec adds a complete local `.pptx` import pipeline to the existing NotebookLM PPT Workbench.

The new pipeline allows the user to upload a local PowerPoint file, normalize it into the workbench's existing intermediate asset model, and then run the current reconstruction flow to produce:

- a display-oriented clone
- an editable rebuild

The implementation is intentionally staged:

1. fully support PPTX files produced by this project and NotebookLM-related exports first
2. then expand compatibility to more generic local `.pptx` files

This keeps the feature aligned with the current V1 product direction: reuse the existing workbench, artifact history, and reconstruction engine instead of creating a separate import-only product path.

## Goals

- Allow a user to upload a local `.pptx` file from the existing project workspace
- Persist import records at the project level
- Convert imported `.pptx` files into a normalized asset bundle that can reuse the current reconstruction engine
- Support the project's own generated PPT outputs and NotebookLM-related exports first
- Provide best-effort import for more generic `.pptx` files
- Keep import history separate from rebuild history while allowing one import to drive multiple rebuilds

## Non-Goals

- Full-fidelity editing of imported PPTX content directly in the browser
- High-fidelity recovery of animations, transitions, SmartArt, or theme masters
- Guaranteed perfect object-level recovery for arbitrary third-party `.pptx` files
- A separate standalone import page or import-only application flow

## Product Scope

The new feature is an additional input path inside the existing workbench.

Current supported path:

- NotebookLM export images plus optional OCR JSON -> reconstruction

New supported path:

- local `.pptx` upload -> normalized import assets -> reconstruction

The rest of the product stays the same:

- project management
- source history
- prompt workflow
- artifact history
- display clone generation
- editable rebuild generation

## User Outcomes

After this feature ships, a user should be able to:

1. open a project in the existing workbench
2. upload a local `.pptx`
3. see that upload recorded in project history
4. trigger reconstruction from the imported file
5. download display clone and editable rebuild outputs

## Supported Import Tiers

### Tier 1: Internal generated PPTX

This includes PPTX files generated by this repository, such as prior display clone and editable rebuild outputs.

This tier is the most controlled and should have the highest success rate.

### Tier 2: NotebookLM-related PPTX exports

This includes NotebookLM-adjacent exported PPTX material that is structurally close to the current workflow.

This tier is the primary business goal because it directly extends the existing semi-automatic workflow.

### Tier 3: Generic local PPTX

This includes PowerPoint, WPS, or other tools that produce standard `.pptx`.

This tier is best-effort in phase one:

- import when possible
- extract slide previews and basic text
- attempt reconstruction
- gracefully degrade if structure is too complex

## Import Flow

The import flow is:

1. user uploads a local `.pptx` in the project workspace
2. the backend stores the file and creates an import record
3. the backend classifies the file as:
   - `internal_generated`
   - `notebooklm_export`
   - `generic_pptx`
4. the backend converts the file into a normalized asset bundle
5. the UI shows the import status and imported slide assets
6. the user triggers reconstruction from the import record
7. the existing reconstruction pipeline generates:
   - display clone
   - editable rebuild
8. the results are saved into the existing artifact and version history areas

## Architecture

### New Service Boundary

Add a `PPTX Import Service` to the agent.

Responsibilities:

- accept uploaded `.pptx`
- classify source type
- extract a normalized asset bundle
- persist import records and slide assets
- pass normalized assets into the existing reconstruction engine

The import service does not own final reconstruction logic.

### Existing Service Boundary

The current reconstruction engine remains responsible for:

- display clone generation
- editable rebuild generation
- layout recovery
- table and icon-card recovery

The reconstruction engine should consume normalized assets, not raw imported PPTX internals.

This boundary is important because it keeps PPTX parsing from leaking into every reconstruction path.

## Normalized Asset Bundle

Each imported presentation should be converted into a normalized bundle that is close to the current image-plus-structure workflow.

Minimum bundle contents:

- slide list
- per-slide preview image path
- per-slide extracted text dump
- optional per-slide structure summary
- import metadata

The structure summary can start small in phase one. It does not need to fully describe every original PowerPoint object.

## Data Model

### ImportedPresentation

Add a project-level import model with fields equivalent to:

- `id`
- `project_id`
- `source_type`
- `filename`
- `original_file_path`
- `status`
- `page_count`
- `created_at`
- `error_message`

### ImportedSlideAsset

Add a child slide-asset model with fields equivalent to:

- `id`
- `import_id`
- `slide_index`
- `preview_image_path`
- `text_dump`
- `structure_json_path`

### Relationship to Existing History

The import history should be separate from rebuild history.

One imported presentation may produce multiple rebuild attempts. This separation makes retries, quality comparison, and future compatibility improvements much easier to manage.

## API Design

Phase one only needs four endpoints.

### `POST /projects/{id}/imports/pptx`

Purpose:

- upload a local `.pptx`
- create an import record
- start import analysis

### `GET /projects/{id}/imports`

Purpose:

- return project-level import history

### `GET /imports/{import_id}`

Purpose:

- return one import record
- include status, source type, page count, and slide assets

### `POST /imports/{import_id}/rebuild`

Purpose:

- trigger display clone and editable rebuild from that imported presentation

Phase one does not need delete, rename, or metadata editing endpoints.

## UI Design

### Workspace Entry Point

Add an `Import PPTX` section inside the existing project workspace.

This section should support:

- selecting a local `.pptx`
- showing upload and analysis state
- showing classified source type
- continuing to reconstruction after import succeeds

This keeps the feature inside the current workbench instead of creating a second parallel UI.

### Import History

Add an `Imported PPTX revisions` area to the existing history/output part of the workspace.

This area should show:

- file name
- source type
- status
- page count
- created time
- action to view details
- action to rebuild

### What Phase One Should Not Add

Phase one should not add:

- a dedicated import page
- inline editing of imported slides
- advanced import parameter controls
- a complex pre-processing wizard

## Status Model

Use a simple import status lifecycle:

- `uploaded`
- `analyzing`
- `ready`
- `rebuilding`
- `completed`
- `failed`

Import failure and rebuild failure must be recorded separately. An import may succeed while a rebuild later fails.

## Parsing and Extraction Strategy

Phase one should prefer reuse over deep rearchitecture.

Recommended implementation strategy:

- use `python-pptx` for object-level text extraction where practical
- generate and store slide preview assets through the current artifact pipeline
- produce a structure summary only where the source is easy to interpret
- pass the normalized slide assets into the existing reconstruction engine

This means phase one is not trying to become a perfect PPT object editor. It is trying to become a robust importer that feeds the current rebuild pipeline.

## Failure and Degradation Strategy

The import pipeline must degrade gracefully.

### Ideal Path

- preview generation succeeds
- text extraction succeeds
- structure summary is usable
- full reconstruction runs

### Partial Degradation

- preview generation succeeds
- text extraction is partial
- structure summary is incomplete
- reconstruction still runs with reduced fidelity

### Lowest Safe Fallback

- the file is accepted as a valid `.pptx`
- the system stores the original file and import record
- slide-level extraction may be incomplete
- the error is recorded clearly
- the user can retry later

The system should avoid whole-file rejection when only part of the deck is difficult to interpret.

## Testing Strategy

Phase one should cover three layers.

### 1. Import Service Unit Tests

Verify:

- source-type classification
- import record creation
- slide asset extraction

### 2. API Tests

Verify:

- `.pptx` upload succeeds
- import history can be listed
- import detail can be fetched
- rebuild can be triggered from an import record

### 3. Frontend Integration Tests

Verify:

- user can select a `.pptx`
- UI shows import state
- import history appears in the workspace
- user can trigger rebuild from the import record

Phase one does not need heavy screenshot-based visual validation for PowerPoint rendering.

## Recommended Sample Set

To verify the feature, prepare at least three sample categories:

1. internal generated PPTX
2. NotebookLM-related exported PPTX
3. generic local `.pptx`

These samples should be used to confirm both successful import and appropriate degradation behavior.

## Phase One Implementation Order

1. add import data models and API skeleton
2. implement the minimum PPTX import service
3. connect imported assets to the existing reconstruction pipeline
4. add workspace UI for PPTX upload and import history
5. verify with the three sample categories

## Success Criteria

Phase one is successful when all of the following are true:

1. the user can upload a local `.pptx`
2. the system creates a persistent import record
3. the system produces a normalized asset bundle
4. the user can trigger display clone and editable rebuild from the import
5. import history is visible at the project level
6. internal generated and NotebookLM-related PPTX files work reliably
7. generic `.pptx` files import on a best-effort basis without breaking the workflow

## Known Boundaries

Phase one still does not guarantee:

- animation or transition recovery
- complete SmartArt fidelity
- exact theme/master preservation
- perfect recovery of arbitrary third-party PPT object graphs
- browser-side editing of imported PPT content

These are acceptable limits for the first version because the goal is complete import-to-rebuild workflow coverage, not universal PPT authoring parity.
